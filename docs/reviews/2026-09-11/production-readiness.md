# MERIDIAN 홈페이지 엔지니어링·프로덕션 준비도 검토

검토일: 2026-09-11 · 대상: 로컬 `feat/menu-ia` · 커밋: `9b6f13c4ab9cb82c1894be684c354395cfd72f49`

## 판단

**전면 재작성은 권하지 않는다. 현재 구조를 유지하면서 문의 접수, 내비게이션, 스크롤 계층을 우선 재설계하는 편이 적절하다.** Next.js App Router, 정적 페이지 생성, 파일 기반 콘텐츠, 작은 API라는 큰 틀은 이 규모의 홈페이지에 맞는다. 관리자 시스템이나 데이터베이스가 없다는 사실만으로 잘못된 아키텍처라고 볼 수 없다.

다만 **현재 코드를 그대로 프로덕션 운영 준비가 완료된 상태로 판단할 수는 없다.** 메일이 실패해도 성공으로 표시되는 실제 결함, 잘못된 세무 일정, 문의 맥락 유실, 키보드 탐색 문제를 확인했다. 개발 도구의 통과 여부와 고객 업무 흐름의 정확성이 분리되어 있다.

디자이너의 경력이나 개발 경험을 근거로 품질을 추정하지 않았다. 입력 크기 제한, HTML 이스케이프, 발행 여부 관리, 경로 검증, 보안 헤더, 의존성 서명 확인, CI 등은 이미 구현되어 있다. 개선의 초점은 이러한 기반을 유지하면서 **실제 접수와 고객 전환을 검증하고, 시각 연출 코드의 결합도를 낮추는 것**이다.

## 우선 수정할 결함

P1은 정상적인 운영 시작 전 해결할 항목, P2는 고객 사용성과 안정성을 위해 뒤이어 해결할 항목, P3는 유지보수 개선 항목으로 사용한다. 보안 감사 도구의 `critical` 등급과 이 문서의 제품 우선순위는 서로 다른 기준이다.

### 1. P1 — 문의 메일이 실패해도 접수 성공으로 표시된다

- 근거: `src/app/api/contact/route.ts:476`, `src/components/contact/contact-form.tsx:57`.
- `await resend.emails.send(...)`의 반환값을 검사하지 않는다. 설치된 SDK는 공급자 거절을 반드시 예외로 던지는 것이 아니라 `{ data: null, error: ... }`로 반환한다.
- 모의 403 응답에서 실제 SDK의 실패 반환을 확인했고, 같은 조건에서 문의 API는 **HTTP 200, `{success:true}`**를 반환했다. 폼은 이를 보고 내용을 비우고 접수 완료를 표시한다.
- 영향: 고객은 문의가 접수됐다고 믿지만 담당자는 문의를 받지 못한다. 현재 전환 흐름에서 가장 먼저 고칠 버그다.
- 조치: `error`와 성공 데이터/메시지 ID 검사, 실패 시 적절한 오류 응답 및 입력 보존. 공급자 거절·timeout·네트워크 실패·정상 접수 테스트 추가. 공급자가 요청을 수락했다는 것과 최종 배달 완료도 구분한다.

Resend 공식 Next.js 예제 역시 반환된 `error`를 확인한다. [Resend 공식 예제](https://resend.com/docs/send-with-nextjs)

### 2. P1 — 현재 의존성 조합이 보안 검사에 실패한다

- 근거: `package.json:21`, `package.json:39`, `package-lock.json`, `.github/workflows/ci.yml:29`.
- `next:16.2.4`, 고정된 `postcss:8.5.10` override 등에서 최신 감사 경고가 발생한다. production dependency만 감사해도 6개가 남는다.
- 현재 CI는 moderate 이상에서 차단하므로 그대로라면 supply-chain job에서 실패하고 후속 검증도 실행되지 않는다.
- 조치: 별도 업데이트 변경으로 Next/ESLint Next 버전을 맞추고 lockfile과 관련 전이 의존성을 갱신한다. PostCSS override도 함께 재검토한다. `npm audit fix --force`만으로 해결했다고 간주하지 않는다.
- 적용성: Windows 전용 문제를 Vercel 운영 서버의 확정 취약점으로 계산하지 않았다. AVIF 처리 문제 역시 실제 이미지 입력 경계와 배포 플랫폼의 이미지 처리 방식을 확인해야 한다. 공격 성공이나 침해를 재현한 것은 아니다.

검토 시 npm은 Next 16.3.4를 수정 후보로 제시했다. 공식 AVIF 관련 공지는 16.3.3을 패치 버전으로 명시한다. [Next.js 공식 보안 공지](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)

### 3. P1 — 문의의 개인정보 처리 고지와 운영 정책이 빠져 있다

## 아키텍처와 비효율

### 스크롤 시스템은 부분 재작성이 필요하다

`src/components/providers/smooth-scroll-provider.tsx:55`의 전역 `ReactLenis`와 `src/components/home/promo-motion.tsx:54`의 `new Lenis`가 홈·포털에 함께 생성된다. 같은 페이지 스크롤에 제어 주체가 둘이다. 일부 컴포넌트는 React context의 Lenis를 멈추고, 다른 연출은 별도 인스턴스로 동작한다.

`PromoMotion`은 668줄의 DOM 조작 코드이며 타입 검사와 lint를 파일 전체에서 꺼 둔다. 전역 selector, 여러 스크롤 이벤트/RAF, 숫자로 박힌 위치 보정에 의존한다. 종료 시 `ScrollTrigger.getAll().forEach(kill)`로 다른 컴포넌트의 trigger까지 제거하고, 전역 scroller proxy의 생명주기도 소유권이 명확하지 않다. 따라서 하나의 연출 수정이 다른 화면의 움직임에 영향을 줄 수 있다. **항상 스크롤이 멈춘다는 주장은 아니다. 구조상 충돌 조건을 줄여야 한다는 판단이다.**

권장 구조는 스크롤 제어 주체 하나, 각 장면의 ref와 범위 안에서만 수행하는 연출, 장면별 초기화/정리다. 기본 스크롤을 기준으로 꼭 필요한 구간에만 연출을 추가하는 방향이 유지보수에 유리하다. GSAP·Motion·Lenis 중 하나만 무조건 남길 필요는 없지만 각자의 책임을 나눠야 한다. 화면 전환 반복, 스크롤 중 이탈, reduced-motion 변경을 테스트해야 한다.

Lighthouse 모바일 시뮬레이션에서 홈 LCP는 9.5초, 타깃은 히어로 video였다. `about-opening.tsx:138`과 `:172`의 영상에는 poster가 없다. CSS와 두 폰트 스타일시트도 초기 렌더링 경로에 있다.

우선순위는 히어로 poster와 안정적인 최초 화면, 불필요한 재마운트 제거, 필수 스타일·폰트 최적화, 보이지 않는 영상의 재생 중지다. 영상 파일 용량만 줄이고 페이지 수명주기를 그대로 두는 접근은 부족하다. TBT 30ms와 CLS 0은 긍정적이며, 로컬 측정값을 실사용자 p75와 혼동해서는 안 된다.

### 콘텐츠 시스템은 유지할 수 있으나 편집 검증이 약하다

MDX는 현재 신뢰된 저장소 콘텐츠다. 외부 사용자가 직접 MDX를 올리는 경로가 없는 현재 상태를 원격 코드 실행 취약점으로 단정하지 않는다. 향후 CMS/외부 기고를 붙일 때는 실행 가능한 MDX와 비실행형 Markdown의 신뢰 경계를 다시 결정해야 한다.

## 프로덕션에 추가로 필요한 것

### 문의 운영의 최소 기준

현재는 폼 요청에서 메일 전송까지 한 번에 처리한다. 접수 ID, 영속적인 문의 상태, 중복 방지, 재시도, 배달 상태 확인, 담당자 알림의 운영 흐름이 없다. 메일 오류를 고친 뒤에도 요청 수락 후 배달 실패를 누가 어떻게 확인할지 정해야 한다.

작은 홈페이지라면 공급자 접수 ID 저장/로그, 실패 알림, 제한된 재시도, 수신함 처리 기준으로 시작할 수 있다. “한 건도 유실하지 않는 접수”가 요구되면 문의 레코드를 먼저 저장하고 outbox/큐로 발송하며 중복 제출을 제어하는 구조가 적합하다. 규모와 요구 수준을 확인하지 않고 대형 CRM이나 별도 마이크로서비스를 도입할 필요는 없다.

`api/contact/route.ts:28`의 공유 rate limit 강제 옵션은 기본값이 false다. Redis 설정 누락·장애 시 프로세스 메모리로 내려가는데 serverless 인스턴스 사이에서 한도를 공유하지 못한다. README에는 이 강제 옵션도 없다. 운영 환경의 fail-open/fail-closed 정책을 정하고 필수 환경변수를 검증해야 한다. 발신 주소가 빠졌을 때 테스트용 `onboarding@resend.dev`로 내려가는 동작도 운영에서는 명시적 설정 오류로 처리하는 편이 낫다. 실제 배포 환경의 설정 누락을 확인한 것은 아니다.

추가로 설치된 Upstash SDK는 기본 5초 timeout 시 예외가 아니라 `success:true, reason:"timeout"`을 반환한다. 네트워크가 끝나지 않는 모의 limiter로 이 반환 형태도 재현했다. 현재 route는 `success`만 읽으므로 강제 공유 옵션을 켜도 이 timeout 경로는 거절하지 못한다. 엄격한 제한이 필요하면 `reason`까지 해석하는 애플리케이션 정책을 구현해야 한다. SDK 옵션 이름이나 `try/catch`만 보고 장애 시 차단이 완성됐다고 판단해서는 안 된다.

### 기능을 검증하는 CI와 배포 절차

CI 자체는 이미 있다. 공급망 감사·서명·SBOM까지 있는 점은 좋다. 부족한 것은 사용자 업무를 검증하는 테스트다.

최소 테스트 묶음은 다음과 같다.

1. 문의: 유효/잘못된 입력, 메일 거절·timeout·정상 응답, rate limit 저장소 장애, 중복 접수.
2. 견적: 매출 구간 경계, 직원 수 경계, 업종·추가 옵션·초기 비용, 공유 링크 왕복 및 중복 입력.
3. 탐색: 데스크톱/모바일 키보드 메뉴, 검색 결과→고객 단계, 서비스/견적→문의, 블로그 분류·FAQ.
4. 렌더링: 주요 URL 200/404, canonical, 자산 경로, 모바일·reduced-motion·JavaScript 실패 시 핵심 정보.
5. 배포 후: 홈페이지/검색 API/문의용 비발송 검증 경로/계약 앱 자산과 리다이렉트의 smoke test.

Vercel에 CI 통과 전 production 승격을 막는 연결, 실제 production branch, 환경별 도메인/Origin 허용 목록, rollback 절차, 에러 담당자를 확인해야 한다. 저장소 CI가 있다는 사실만으로 Vercel 배포가 그 결과에 의해 차단된다고 볼 수 없다.

### 장애 복구와 관측

`error.tsx`, `global-error.tsx`, 맞춤 `not-found.tsx`가 없다. 기본 404는 정상 동작하므로 페이지가 없으면 무조건 500이라는 뜻은 아니다. 실제 오류 시 한국어 안내, 다시 시도, 직접 문의 경로를 제공하는 것이 좋다.

Vercel Analytics와 SpeedInsights는 이미 붙어 있다. 여기에 문의 시도/성공/실패, 공급자 오류, 검색 API 실패, JS 예외, 외부 앱 연결 상태를 관측하는 체계를 보완한다. 로그에는 문의 본문이나 인증정보를 남기지 않고 상관관계 ID와 오류 종류를 남긴다. 검색 fetch 실패를 빈 결과처럼 삼키는 `site-search.tsx:49`도 로딩·실패·결과 없음 상태로 구별한다.

### 실제 대시보드와 계약 시스템의 별도 수용 검사

`/portal`의 숫자와 화면은 데모 마크업이며 실제 업무 데이터 시스템은 `siteConfig.clientPortalUrl`의 별도 앱이다. `/contract`도 `next.config.ts:82`부터 별도 계약 앱으로 프록시한다. 이 분리 자체는 타당하다. 홈페이지에 대시보드 DB나 인증을 중복 구현할 이유는 없다.

현재 검토에서 두 앱의 진입 응답과 계약 헤더 분리는 확인했지만, 다음 기능은 본 저장소만으로 인증할 수 없다.

- 고객 로그인/탈퇴, 회사별 데이터 권한 분리, 사용자 초대와 권한 변경.
- 홈택스·카드·통장 수집의 실제 주기, 실패·지연·재시도와 기준 시각.
- 장부·세금 산출의 정확성, 대시보드 홍보 문구와 실제 제공 범위의 일치.
- 계약 본인 확인, 카메라·업로드, 서명, 문서 보존·열람·삭제, 감사 기록.
- 환경별 설정, 외부 앱 장애 시 고객 안내, 연결 도메인/쿠키/CSP/리다이렉트 호환성.

특히 `/contract` 헤더 예외는 이미 카메라 권한 충돌을 피하기 위해 구현되어 있다. 이를 무조건 제거하거나 홈페이지 CSP를 덮어씌우는 수정은 오히려 회귀를 만들 수 있다.

## 유지·수정·재작성의 경계

| 영역 | 권장 | 이유 |
|---|---|---|
| Next.js App Router / 라우팅 | 유지 + 보안 업데이트 | 사이트 규모와 정적 페이지 특성에 적합 |
| MDX 콘텐츠 / 정적 생성 | 유지 + schema·편집 검토 보완 | 51개 글에 충분, CMS는 편집 수요에 따라 결정 |
| 가격 계산 도메인 | 유지 + 입력 경계·테스트·버전 | 순수 계산 함수로 UI와 분리된 점은 좋음 |
| 문의 API와 운영 흐름 | 부분 재설계 | 성공 판정 결함과 추적·복구 공백 |
| 메뉴·모달·탭·검색 상태 | 부분 재작성 | 각 위젯의 표준 키보드·URL 계약이 부족 |
| 홈·포털 스크롤 엔진 | 우선 부분 재작성 | 중복 제어, 전역 DOM/trigger 소유권 불명확 |
| 페이지 콘텐츠·기존 디자인 | 대체로 유지 | 기능 버그를 해결하려고 디자인 전체를 버릴 필요 없음 |
| 전역 CSS | 단계적 모듈화 | 수정 파급 범위를 줄이고 토큰 중복 제거 |
| 실제 대시보드·계약 앱 | 별도 감사/테스트 | 다른 저장소의 업무 시스템이며 현재 범위로 품질 보장 불가 |

리팩터링 시 `app`은 라우팅·메타데이터·조립, 문의/견적은 각 기능의 타입·검증·서비스, 시각 연출은 화면별 컴포넌트로 책임을 나누면 충분하다. 폴더를 많이 만드는 것보다 “누가 데이터를 검증하고, 누가 상태와 스크롤을 소유하는가”가 명확해야 한다.

## 독립 조사 통합

별도의 `claude-showni` 세션을 `--model fable`로 실행했고 세션 기록의 실제 모델 ID가 **`claude-fable-5-1`**임을 확인했다. 세션 ID는 `29d01bc0-59b6-4327-b690-c99b6aca6394`다. 각자 상대 보고서를 읽지 않은 상태에서 조사했으며, Codex의 [독립 메모](./codex-independent.md)를 먼저 저장한 다음 [Fable 독립 보고서 원문](./fable-independent.md)을 읽고 통합했다. Fable은 소스·로컬 문서·읽기 전용 HTTP를 검토했고, Codex는 빌드·감사·브라우저·SDK 모의 검증까지 수행했다.

| 구분 | 통합 결과 |
|---|---|
| 양쪽 공통 판단 | 전면 rewrite 불필요. App Router/MDX/정적 생성 유지. 스크롤 소유권, 문의 전달 계약, 접근성, 개인정보 안내, 세무 일정, SEO, 테스트·운영 관측 보완 필요. |
| Codex가 추가로 확인한 실제 실패 | Resend 거절에도 HTTP 200, 중복 공유 견적 합산, 고객 검색의 다른 탭 도착, 모바일 포커스 탈출, Upstash timeout의 성공 반환, 현재 의존성 감사 실패. |
| Fable 추가 발견 → Codex 재검증 | 문의 허용 목록과 서비스명/산출물 계약 불일치, 블로그 3페이지에서 뒤로 가면 1페이지로 복귀, 푸터 직함 중복, FAQ 직렬화 차이, 추적 중인 생성물. |
| 두 조사에서 구조적 위험으로 판단 | 이중 Lenis, 전역 trigger 정리, hydration 시 트리 교체. 충돌 가능성의 근거이며 모든 사용자에게 항상 실패한다는 뜻은 아님. |

독립 보고서는 검토 당시 원문을 보존했다. **최종 우선순위와 사실 판단은 이 통합 보고서를 따른다.** 특히 다음은 원문의 주장 강도를 조정했다.

- 공개 글은 51개다. 검색 번들에 포함된 MDX 54개와 공개 글 수를 혼동하지 않는다. 기본 OG 이미지 부재가 모든 글의 이미지 부재를 뜻하지 않는다.
- Fable의 초기 렌더링/CLS 우려는 구조적 가능성이다. 이번 Lighthouse의 실제 CLS는 0이었다. 이중 스크롤 제어가 특정 연출을 언제나 무력화한다는 단정도 채택하지 않았다.
- canonical은 검색엔진에 주는 힌트이며 잘못된 값이 특정 순위/색인 제거를 확정하지는 않는다. 비공개 의도의 가격 페이지나 빈 사례 분류는 의도와 편집 상태를 확인해 우선순위를 정한다.
- 개인정보 동의 체크박스가 모든 처리에서 무조건 필요한 것으로 단정하지 않았다. 실제 처리 근거와 흐름을 확정한 뒤 해당 고지·동의·방침을 구현해야 한다.
- 문의에 데이터베이스·CRM을 반드시 도입해야 한다는 결론은 아니다. 유실 허용 수준에 따라 공급자 접수 ID와 관측부터 영속 outbox까지 필요한 범위를 정한다.
- 운영 CDN 캐시, 별도 업무 앱의 내부 기능, Safari 실기기 품질은 이번 결과만으로 인증하지 않는다. Next 기본 오류 화면이 존재하므로 사용자 정의 error 파일이 없다는 이유로 모든 오류를 빈 화면이라고 하지 않는다.


## 한계

이 검토는 소프트웨어 품질과 운영 준비도를 대상으로 한다. 51개 세무 글의 모든 법적 판단, 실제 세무 자문 내용, 대시보드의 산출 숫자 정확성을 전수 인증하지 않았다. 보안 침투 테스트, 운영 계정·환경변수·DB·메일 로그 감사, 실제 계약 제출도 하지 않았다. WebKit의 보조 smoke 검사는 수행했지만 Safari 실기기와 보조공학 전수 검사는 별도로 필요하다. 로컬 HTTP/브라우저 통과와 외부 URL 200을 전체 업무 시스템의 정상 작동 보증으로 사용해서는 안 된다.
