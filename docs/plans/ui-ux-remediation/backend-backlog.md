# 백엔드·외부 연동 후속 목록

작성: 2026-09-11 · [UI/UX 실행 계획](./README.md)의 별도 인계 문서.

**이번에는 아래 API·DB·운영 연동을 구현하지 않는다.** 소스에 실제 존재하는 서버 기능과 프론트 데모를 구분한다. 후보 API 경로는 향후 설계 예시이며 이미 존재하거나 도입이 확정된 것으로 해석하지 않는다.

## 1. 현재 기능 분류

| 기능 | 확인된 구현 | 이번 프론트 작업 | 서버 측 후속 판단 |
|---|---|---|---|
| 문의 제출 | `POST /api/contact` 존재, Resend·Upstash 사용 | 초안·선택 요약·입력 검증·응답별 UX | 신규가 아닌 기존 API 수정 필요 |
| 사이트 검색 | `GET /api/search` 존재, 서비스/고객/콘텐츠 목록 반환 | loading/error/empty/키보드·도착 탭 수정 | 지금 새 검색 서버 불필요 |
| 예상 수임료 계산 | `src/lib/pricing.ts`의 로컬 계산 | 경계값·URL·공유·문의 연결 | 참고 견적이면 서버 불필요. 확정 견적 저장 요구 시 별도 |
| 홈 대시보드 미리보기 | `dashboard-peek.tsx`의 예시 숫자/표시용 마크업 | 레이아웃·가독성·예시 캡션 보존 | 영업용 미리보기를 위해 실제 금융 API를 만들 필요 없음 |
| 포털 화면/통계/근거·기간 선택 | 정적 마크업, `promo-motion.tsx`의 예시 데이터와 DOM 변경 | React 상태로 정리, 선택·키보드·예시 표기 | 실제 데이터 제공으로 바꾸는 경우에만 별도 연동 필요 |
| 대시보드 메뉴·검색처럼 보이는 요소 | 홈 미리보기 일부는 `<p>`/`<span>` 장식. 실제 기능 아님 | 데모 전체 맥락 명확히, 가짜 입력/버튼처럼 초점이 가지 않게 처리 | 클릭 가능하게 보이는 모든 요소를 UI-00에서 목록화 |
| 고객 단계·FAQ·진단 콘텐츠 | 로컬 상태/정적 데이터 | 탭·URL·펼치기·문의 이동 | 서버 기능을 새로 만들 이유 없음 |
| 블로그·사례 | 저장소 MDX·정적 생성 | 필터/history·빈 사례 안내·검토 workflow | CMS는 편집 운영 수요가 생기면 검토 |
| 세무 일정 | 두 파일의 정적 배열 | 단일 승인 데이터·D-day·만료 안내 | 자동 갱신 API는 선택 사항 |
| 실제 고객 대시보드 | `siteConfig.clientPortalUrl`의 별도 앱 | 명확한 진입 CTA·외부 이동 안내 | 내부 백엔드 유무·품질은 본 저장소로 판단 불가 |
| 계약 | `/contract`가 별도 앱으로 프록시됨 | 진입 경로·새 창/리다이렉트 확인 | 내부 계약 서버·서명·보관은 별도 조사 |

홈 캡션에 이미 “표시된 숫자는 예시입니다”가 있다. 이를 없애거나 로그인한 고객의 실제 값처럼 표현하지 않는다. API가 없다는 사실만으로 영업용 데모를 미완성 기능으로 분류하지 않는다. 반대로 눌러도 아무 반응 없는 요소를 실기능으로 설명하지 않는다.

## 2. 인계 항목

### BE-01 — 기존 문의 API의 실제 성공 판정과 전달 계약

- 상태: **기존 API 결함 확인. 실제 문의 운영의 우선 차단 항목.** UI 작업 후에도 미해결로 남는다.
- 근거: `src/app/api/contact/route.ts`, `src/lib/contact-options.ts`. 공급자 `{data:null,error}`를 확인하지 않아 실패에도 200 반환. 서비스 표시명·산출물과 서버 옵션 계약도 불일치.
- 작업: 공급자 실패/timeout/네트워크 예외 처리, 메시지 ID 확인, 안정적인 service ID·견적 버전·요약의 서버 검증과 매핑. `output`/`desiredOutput` 표준화, 기존 단순 message 요청 호환.
- 계약 후보: 성공에 접수 상태와 추적 ID, 실패에 사용자 안내용 error code·필드 오류·필요 시 재시도 시간. 공급자 수락과 최종 배달 완료를 구분한다. 정확한 필드/상태 코드는 백엔드 구현 때 확정한다.
- UI 준비: 기존 message에 사용자가 확인한 요약을 포함할 수 있게 설계. mock 성공/실패 테스트와 실제 연동 테스트를 구별.
- 수용 검사: 공급자 403·timeout·중복 클릭·유효/잘못된 입력 테스트. 실패를 성공으로 반환하지 않음. 실제 검증은 승인된 테스트 수신함에서 수행.

### BE-02 — 문의 유실·중복·rate limit·운영 설정

- 상태: 영속 접수/중복 방지/배달 추적은 미구현, 공유 제한과 fallback은 존재하나 운영 정책 보완 필요.
- 작업: 필요한 접수 보장 수준 결정. 단순 공급자 ID·실패 알림으로 충분한지, 먼저 저장 후 발송/outbox가 필요한지 판단. DB·큐·CRM은 자동 전제하지 않는다.
- 공유 limiter의 설정 누락·저장소 장애·SDK `success:true, reason:"timeout"` 경로까지 포함해 fail-open/fail-closed 정책 구현. 운영 발신 주소 누락 시 테스트 주소 fallback 방지. 필수 env 이름·검증 절차만 문서화하며 값은 기록하지 않는다.
- 계약 후보: idempotency key와 재시도 의미, 접수 상태 조회가 실제 필요한 경우 조회 계약. 인증 없는 문의 전체 목록 API를 만들지 않는다.
- UI 준비: 제출 중 버튼 상태·입력 보존·불확실한 접수 상태 안내. 프론트 버튼 비활성화는 서버 중복 방지의 대체가 아님.
- 수용 검사: 다중 인스턴스·동시 제출·공급자 지연·저장소 장애 후 처리 결과를 추적 가능.

### BE-03 — 검색 API 신뢰성 / 선택적 확정 견적 기능

- 검색: 기존 API를 유지한다. 필요하면 응답 schema·실패 code·콘텐츠 버전·캐시를 보완한다. 프론트는 오류와 빈 결과를 구분할 수 있어야 한다. 검색 때문에 새 DB나 검색 엔진을 도입하지 않는다.
- 견적: 현재는 브라우저 참고 계산이다. 예약·주문·청구 금액의 근거로 쓰려면 서버 권위 계산, 가격표 버전, 유효 기간, 확정 ID가 필요하다. `POST /api/quotes` 같은 엔드포인트는 그 요구가 생겼을 때의 후보이며 이번에 만들지 않는다.
- 수용 검사: 공개 콘텐츠만 검색, 잘못된 결과 경로 없음. 확정 견적 기능 도입 시 클라이언트가 보낸 금액을 신뢰하지 않고 서버에서 검증.

### BE-04 — 실제 대시보드 앱 확인 또는 연동

- 상태: 외부 앱 진입만 확인됨. 로그인·회사별 권한·수집·계산·보고서 API는 미검증. “백엔드가 없다”고 단정하지 않는다.
- 후속: 외부 저장소/운영 책임자를 확인하고 실제 존재 API를 목록화한 뒤 부족한 항목만 설계한다. 회사별 데이터 격리, 기간별 요약, 세액 근거/거래 원장, 수집 상태·기준 시각, 오류·갱신 지연 계약이 대상.
- UI 준비: 홈페이지는 데모와 외부 진입을 유지한다. 고객 실데이터를 홈페이지에 옮기지 않는다. 데모 기간 선택은 선택에 맞는 일관된 예시 값만 보여준다.
- 내용 확인: “실제 고객 화면”, “매일 자동 수집”, 제공 범위 문구가 외부 앱의 실제 기능과 일치하는지 담당자가 확인. 확인 없이 제공 약속을 확대하지 않는다.

### BE-05 — 계약 앱

- 상태: 별도 앱 프록시. 계약 생성·본인 확인·서명·파일 저장·문서 상태 API는 이번 범위에서 미검증.
- 후속: 외부 시스템의 기존 계약을 먼저 확인. 서명·업로드·카메라 권한, 보관/열람, 권한, 실패/재시도, 감사 이력을 별도 수용 검사.
- UI 준비: 실제 계약을 자동 제출하지 않고 진입·리다이렉트·화면 로딩을 확인한다. 기존 `/contract` 카메라 헤더 예외를 보존. 홈페이지 CSP 일괄 변경으로 외부 앱을 깨뜨리지 않는다.

### BE-06 — 콘텐츠·세무 일정 자동화 (선택)

- 상태: 정적 파일로 충분히 운영 가능한 기능. 백엔드 부재 자체는 결함 아님.
- 후속: 비개발자의 잦은 편집·승인·자동 일정 갱신이 필요할 때 CMS/승인 workflow/공식 소스 동기화를 검토한다. 출처·대상·검토일·만료·예외 일정 책임자를 먼저 정한다.
- UI 준비: 승인된 정적 일정으로 정정, 만료/사례 없음 상태 제공, MDX 참조·검토일 검사.
- 주의: 휴일 계산기만으로 모든 세무 일정 예외를 확정하지 않는다. 자동 수집 실패 시 마지막 검토 시각과 만료 상태가 필요하다.

### BE-07 — 기존 문의 폼 정보 처리 안내의 내용 확정

- 상태: 사용자 지시에 따라 이번 UI 수정의 별도 개인정보 시스템 개발·회원 기능·필수 동의 절차 추가에서 제외.
- 기록 이유: 현재 코드에는 이름·이메일·전화번호·본문을 받는 문의 폼이 존재한다. 회원가입 여부와 별개의 실제 데이터 흐름을 잊지 않기 위한 기록이다.
- 후속 내용 결정: 문의 폼을 유지하는지, 연락처 처리 주체/목적/보관 방식/문의 창구와 외부 메일 처리에 관한 안내가 무엇인지 실제 운영 기준으로 확정한다. 법적 적용이나 문구를 이번 코드 계획에서 단정하지 않는다.
- UI 연결: 확정된 짧은 안내가 있으면 기존 폼 디자인 안에 배치한다. 확인되지 않은 보유 기간·업체 관계·필수 체크박스를 임의로 만들지 않는다.

### BE-08 — 관측·배포 운영

- 상태: Analytics/SpeedInsights·CI는 이미 존재. 공급자 실패·문의 접수 추적·운영 경보와 배포 gate 연결은 추가 확인 필요.
- 후속: 오류 종류·상관관계 ID 기반 서버 로그, 담당자 알림, 환경별 Origin·도메인·필수 설정, 실제 배포 브랜치·CI 통과 전 승격 차단·rollback 절차 확인. 문의 원문이나 비밀값을 관측 로그에 남기지 않는다.
- UI 준비: 재시도 가능한 오류 화면, 검색 오류 구별, 클라이언트 오류 수집 연결 지점. 새로운 수집 서비스 도입은 서버/운영 계획으로 남긴다.
- 인수: 운영 HTTPS에서 CSP·CDN·외부 앱 자산 확인. 비발송 smoke 경로는 도입 필요성을 별도로 판단하고 공개 운영용 우회 기능으로 만들지 않는다.

## 3. 이후 구현에 넘길 최소 자료

각 항목에 담당 영역, 기존/신규/외부 여부, 재현 절차, 요청·응답 예시(가짜 데이터만), 실패 상태, UI가 기다리는 계약, 수용 테스트, 미결정 사항을 붙인다. BE-01/02가 남으면 “문의 신뢰성 확보 완료”로 표시할 수 없다. BE-04/05의 외부 앱 미검증을 홈페이지 UI 완료와 섞지 않는다.
